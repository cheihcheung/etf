# 多资产策略回测系统 · 项目分析报告

> 分析日期：2026-11-19
> 分析范围：仓库全部源码（web/、desktop/）、文档（docs/）、数据库脚本与运行数据
> 分析方式：静态阅读代码 + 文档交叉比对（未启动服务、未执行回测）

---

## 一、结论摘要

这是一个**面向个人 ETF 投资者的「多资产动态配置 + 双策略回测 + 参数寻优」工具**。它把「越跌越买、越涨越卖」的网格思想（策略 A）与「按年化收益偏离中枢做估值加减仓」的思想（策略 B）固化成可配置规则，在历史行情上逐日模拟执行，并输出收益、回撤、夏普等指标和可视化图表。

项目有**两套完全独立的实现**：

| 版本 | 定位 | 架构 | 状态 |
| --- | --- | --- | --- |
| `web/` | 网页版 / 可部署到服务器 | BS：Vue3 + Express + MySQL | **功能完整**，双策略、费用、流水、多源数据、寻优均可用 |
| `desktop/` | Windows 桌面版 / 免安装数据库 | CS：Electron + SQLite + Vue3 | 界面与交互完整，但**回测内核是简化版**，不支持双策略/费用/流水 |

**最重要的一条发现**：桌面版的回测引擎与网页版不是同一套逻辑。桌面版只做「按初始比例买入并持有」，会忽略前端传来的 `strategyAConfig / strategyBConfig / rebalanceConfig / strategyPriority / centralAnnual`，也不计手续费、不产生调仓流水。桌面版 UI 仍展示「策略组合、再平衡、策略优先级、调仓明细」，因此**用户会误以为策略已生效**。这是当前项目最高优先级的问题（P0）。

## 二、项目定位与业务价值

### 2.1 解决什么问题

个人长期 ETF 投资者常见的痛点：

1. 知道「跌了该加仓、涨了该减仓」，但手工计算每只标的该买卖多少股非常繁琐；
2. 容易情绪化操作，无法严格执行预设规则；
3. 凭感觉配置比例，缺少历史数据验证；
4. 参数（回撤档位、再平衡阈值、年化中枢）凭感觉定，无法量化比较优劣。

系统把上述流程产品化：**配置资产 → 设定比例与档位 → 回测验证 → 参数寻优 → 查看净值/回撤/持仓变化**。

### 2.2 目标用户

- 有 3~6 只 ETF 组合、做长期资产配置的个人投资者；
- 想验证「网格加仓 / 估值择时」策略有效性的量化爱好者；
- 需要向客户演示配置方案效果的投顾人员（docs 中有推广方案、视频方案，说明有对外传播意图）。

### 2.3 功能地图

| 页面 | 路由 | 核心能力 |
| --- | --- | --- |
| 回测与参数寻优 | `/backtest` | 回测参数、单次回测、参数网格寻优、结果图表、调仓明细、历史记录 |
| 股票管理 | `/config` | ETF 增删改查、行情同步、历史数据同步、同花顺 xls 导入、初始比例配置、启用/禁用、对比基准、缩小倍率、专属步长 |
| 策略配置 | `/strategy` | 策略 A 回撤档位（倍数模型）、策略 B 高估/低估档位与年化中枢 |
| 历史走势 | `/history` | 单只 ETF 的 K 线图 + 日行情表格 |

## 三、技术架构

### 3.1 总体结构

```
etf/
├── web/                        # BS 版（代码不共享）
│   ├── client/                 # Vue3 + TS + Vite5 + Element Plus + ECharts
│   │   └── src/{api,components,router,utils,views,types}
│   └── server/                 # Express4 + MySQL8 + mysql2 + winston
│       ├── src/{config,models,routes,services,utils}
│       └── scripts/optimize_runner.js   # 离线 504 组合寻优脚本
├── desktop/                    # CS 版（代码不共享）
│   ├── main.js / preload.js    # Electron 主进程 / contextBridge
│   ├── src/{database.js,ipc-handlers.js,models,services,spider.js,utils.js}
│   └── client/                 # Vue3 前端（Hash 路由 + IPC）
├── docs/                       # 9 篇文档 + 建表脚本 + 需求/推广/视频/手册
├── Table.xls                   # 仓库根目录遗留样例数据（465 KB）
├── .gitignore
└── README.md
```

### 3.2 通信与分层

- **web**：`client` 仅用 axios 走 HTTP；`server` 按 `routes → services → models(BaseModel)` 分层；所有响应统一 `{ success, data, message }`。
- **desktop**：`renderer → preload(contextBridge) → ipc-handlers → models/services → better-sqlite3`；窗口无边框、自定义标题栏；生产环境用自定义 `app://` 协议加载静态资源，路由必须用 `createWebHashHistory()`。

### 3.3 数据来源

| 用途 | 数据源 | 说明 |
| --- | --- | --- |
| 实时报价 | 腾讯 `qt.gtimg.cn` | GBK 编码，需 iconv-lite 解码；按 51/56→sh、15/16→sz 拼前缀 |
| 历史 K 线 | 腾讯 `web.ifzq.gtimg.cn` fqkline | 前复权 `qfq` |
| 历史 K 线（备用/主源） | 东方财富 `push2his.eastmoney.com` | `fqt=1` 前复权，按 secid 区分沪深 |
| ETF 搜索 | 东方财富 `searchadapter.eastmoney.com` | 按关键字联想 |
| 本地导入 | 同花顺导出 xls/xlsx | 服务端 multer + xlsx 解析，按列位置读取；桌面版走原生对话框 |

web 端「同步历史数据」支持 `merge / eastmoney / tencent` 三种模式：按自然年切片抓取（`splitYears`），东财为底、腾讯补缺，逐行 upsert。**注意**：同步是「逐行 findOne + create/update」，几千行 × 多标的会产生大量数据库往返，速度偏慢。

### 3.4 数据库设计（6 张表）

| 表 | 作用 | 关键点 |
| --- | --- | --- |
| `stock` | ETF 基础信息 + 实时价 + 初始占比 | 唯一键 `code`；`is_enabled` 物理风控；`step_ratio` 专属步长；`is_benchmark` 对比基准；`scale_factor` 价格缩小倍率；`annual_return` 目标年化 |
| `history_data` | 历史日 K | 唯一键 `(etf_code, trade_date)`；三索引 |
| `strategy_a_config` | 策略 A 档位 | `trigger_type ∈ {drawdown, rally}`；`ratios` 存 JSON「倍数」对象 |
| `strategy_b_config` | 策略 B 档位 | `deviation_type ∈ {overvalued, undervalued, global_config}`；中枢值借 `global_config` 行存于 `threshold` |
| `trade_records` | 调仓流水 | 类型枚举 init/rebalance/strategy_a/strategy_b/manual/backtest |
| `backtest_results` | 回测结果排行 | `params` JSON；`daily_detail` 为 longtext 大字段（每日净值序列） |

设计上**没有外键约束**，靠应用层维护关联；没有用户表/鉴权，属单机或单租户工具定位。

## 四、回测引擎详解（web 版为核心实现）

核心文件：`web/server/src/services/backtest.js`（约 1400 行，全项目最有价值的部分）。

### 4.1 主流程（9 个阶段）

1. **禁用资产自清洗**：查 `stock.is_enabled = 0`，从入参 `etfs` 与 `initialRatios` 中物理剔除，防止前端脏参数带入。
2. **加载专属步长表**：`stepRatios[code] = stock.step_ratio ?? 5`。
3. **锁定对比基准**：取 `is_benchmark = 1` 的标的；没有则不启用基准（不再兜底 510300）。
4. **读取历史行情**：优先本地 `history_data`，缺失回退爬虫；按 `scale_factor` 除权处理。
5. **生成全局日期轴**：合并所有标的与基准的交易日并排序，停牌日靠价格记忆填充。
6. **首日建仓**：按初始占比、收盘价、100 股一手向下取整；首日未上市标的份额置 0，等待延迟建仓。
7. **逐日主循环**：
   - 更新当日价格 + 维护 `lastValidPrices`（停牌沿用最近有效价，绝不归零）；
   - 延迟建仓（标的首次出现有效价时，按当前总市值 × 初始比例补仓）；
   - 更新历史净值高点、计算当前回撤；
   - 判断是否为调仓评估日（daily 每日 / weekly 周五 / monthly 月末最后交易日）；
   - 策略 A、策略 B 研判 → 决策融合 → `executeTrades`；
   - 日常再平衡（当天已有策略交易则跳过，避免二次扣费）；
   - 记录每日净值、现金、持仓市值、资产占比。
8. **指标计算**：组合、基准、每只 ETF 三套指标 + 历年盈亏统计。
9. **持久化**：`backtest_results` 写指标与 `daily_detail`；`trade_records` 写流水（寻优模式跳过）。

### 4.2 关键规则与实现细节

| 规则 | 实现 |
| --- | --- |
| 一手取整 | 买入 `floor(金额/价格/100)*100`；卖出 `ceil(...)`（向零），避免超卖 |
| 先卖后买 | `executeTrades` 先执行全部卖出回笼现金，再执行买入 |
| 现金不足 | 买入按 `floor(现金*0.999/价格/100)*100` 降级，标记「(现金受限)」 |
| 手续费 | `amount * rate / 100`；`rate=0.03` 表示 **0.03%**；不免五时单笔最低 5 元 |
| 停牌处理 | 沿用 `lastValidPrices`，不参与偏离研判 |
| 未来数据 | 只使用当日收盘价；首日未上市不建仓，杜绝穿越 |
| 再平衡优先 | 优先级为 `rebalance` 且当日有再平衡偏离时，压制 A/B 信号，先做再平衡 |
| 档位复位 | 创新高且 `resetOnHigh` 时回到初始比例并清零档位；再平衡回到初始比例也清零 |
| 策略 B 稳定期 | 回测开始前 0.5 年不运行，避免年化外推放大误触发 |

### 4.3 策略 A（净值回撤/反弹档位）

- 锚：组合历史最高净值；回撤 = `(历史高点 - 当前净值)/历史高点`。
- 档位按 `threshold` 降序扫描，命中第一个 `drawdown >= threshold` 的档位为期望档位。
- **倍数模型**：档位里保存的是「倍数」，实际目标占比 = `initialRatio + 倍数 × step_ratio`。所以改一个步长，所有档位自动联动。
- 期望档位 > 当前档位 → 加仓（drawdown）；期望档位 < 当前档位 → 直接降到匹配档位（rebound），期望档位 0 → 回初始比例；相等 → 不动。
- 主循环额外承担「创新高复位」的唯一入口（函数内部已移除冗余判断）。

> 文档 `06-策略算法文档.md` 第 4.2 节仍描述旧的「多跨一档才退档」逻辑，与当前代码「直接降到匹配档位」不一致，属**文档漂移**。

### 4.4 策略 B（年化中枢偏离）

- 用自然日计算已流逝年数，`当前年化 = CAGR(区间总收益, 年数)`。
- `偏离度 = 当前年化 - 中枢年化`；`≥ 阈值` 命中高估档（减仓），`≤ -阈值` 命中低估档（加仓）。
- 仅当档位级别变化时才调仓，支持在高估/低估之间自然升降与回归 0。

### 4.5 决策融合

- A/B 同日触发：按 `strategyPriority`（strategy_a / strategy_b）二选一；
- 只触发一个则执行该策略；
- `rebalance` 优先模式下，若同日再平衡已超阈值，则压制 A/B，交给再平衡统一对齐 `activeTargetRatios`；
- 当天已执行策略交易则跳过再平衡，保证一天只扣一次摩擦成本。

### 4.6 指标公式

| 指标 | 公式/口径 |
| --- | --- |
| 总收益 | `(期末净值 - 初始资金)/初始资金 × 100%` |
| 年化收益 | `((1+R)^(1/年数) - 1) × 100%`，年数按自然日/365 |
| 最大回撤 | 逐日维护历史高点，取最大跌幅 |
| 年化波动率 | 日收益率样本标准差 × √252 |
| 夏普比率 | `(年化 - 2.5)/年化波动率`，无风险利率固定 2.5% |
| 基准/单 ETF 指标 | 把价格序列折算成「同等初始资金」的净值后同法计算 |

### 4.7 参数寻优

- **在线（UI）**：仅两个维度——再平衡阈值、策略 B 年化中枢；递归笛卡尔积，逐个串行回测，按「年化降序 + 回撤升序」排序，返回前 50 + 最优参数，支持「一键应用」。
- **离线（scripts/optimize_runner.js）**：初始比例 20% 步长枚举 + 再平衡阈值 3 档 + 8 种策略开关组合 = **504 组**，输出带夏普/卡玛的 CSV。README 与概述里说的「504 组寻优」实际指这个脚本，不是 UI。
- **防爆盘**：寻优强制 `isOptimization=true`，不写 `daily_detail`、不写流水。

## 五、web 版与 desktop 版差异对照（重点）

| 能力 | web | desktop | 影响 |
| --- | --- | --- | --- |
| 策略 A / B | 完整实现 | **忽略**（runBacktest 未解构相关参数） | 桌面版实际为「买入持有」回测 |
| 日常再平衡 | 支持 | **不支持** | 目标比例漂移不修正 |
| 手续费 | 支持费率与免五 | **完全不收费** | 收益被高估 |
| 调仓流水 | 生成并入库 | `tradeRecords: []` | 前端「调仓明细」永远为空 |
| 一手取整 | 100 股向下取整 | `floor(金额/价格)` 不取整 | 与实盘不符 |
| 延迟建仓/停牌记忆 | 支持 | 仅按首价近似 | 数据连续性弱 |
| 对比基准 | `is_benchmark` 可配 | **硬编码 000300** | 无法自定义基准 |
| 缩小倍率 `scale_factor` | 支持 | 不支持 | 特殊价格序列会失真 |
| 寻优维度 | 再平衡阈值 / 年化中枢 | 同样两维，但引擎不消费 | **所有组合结果完全相同** |
| 寻优排序 | 年化优先、回撤次之 | 夏普优先 | 结论口径不一致 |
| 结果详情 | 完整 `daily_detail` | 写 `dailyValues`，结构不同 | 两个版本记录不可互通 |
| 数据导入 | 上传 xls | 原生对话框预览/保存 | 平台差异合理 |

桌面版前端（`desktop/client/src/views/Backtest.vue`）仍在组装 `strategyAConfig / strategyBConfig / rebalanceConfig` 并通过 IPC 发送，但主进程的 `BacktestService.runBacktest` 只解构 7 个基础字段，**策略配置被静默丢弃**。这属于「界面承诺了能力、后端没有实现」，比功能缺失更危险。

## 六、工程质量评估

### 6.1 做得好的地方

1. **注释密度极高**：主流程、模型、路由几乎逐行解释设计与「为什么」，对新手友好（符合项目一贯风格）。
2. **防穿越意识明确**：只用当日及以前数据、首日未上市延迟建仓、停牌价格记忆。
3. **边界处理完整**：一手取整、先卖后买、现金不足降级、卖出不超持仓、费用免五。
4. **决策融合设计**：把「信号」与「交易」分离，一次性对齐目标，避免重复扣费，是架构上的亮点。
5. **防爆盘机制**：寻优不落大字段与流水，避免数据库膨胀。
6. **双端独立彻底**：没有共享包，web 走 HTTP/MySQL、desktop 走 IPC/SQLite，各自可独立演进。
7. **文档体系完整**：需求、架构、API、算法、部署、目录、用户手册、推广方案齐全。

### 6.2 主要风险与问题（按优先级）

#### P0：桌面版策略内核缺失

- 位置：`desktop/src/services/backtest.js`。
- 表现：不读策略配置、不计费、无流水、无再平衡、无一手取整、基准写死。
- 后果：桌面版用户得到的是「资产配置买入持有」结果，却按「双策略回测」理解，结论可能完全错误。
- 建议：要么把 web 引擎逻辑同步到 desktop（数据结构、费用、档位、再平衡全量对齐），要么在桌面版明确禁用/隐藏策略相关入口并标注「仅买入持有回测」。**在修复前不建议对外发布桌面版**。

#### P0：桌面版寻优结果无意义

- 寻优维度（再平衡阈值、年化中枢）恰好都是桌面引擎不消费的参数，导致 50 组结果数值相同，排序也无意义。
- 建议：随 P0 一并修复；或桌面版先下线寻优。

#### P1：性能

1. 主循环内 `data.find(d => d.tradeDate === date)` 每天每标的一次线性扫描，15 年 × 5 标的约数千万次比较；标的和年限增加会明显变慢。建议预建 `Map<date, price>`。
2. 同样问题存在于基准日查找、`getPrice`（桌面版）。
3. 寻优串行 `await` 回测，UI 请求可能长时间挂起（无进度推送、无超时/取消）。建议：任务队列 + 进度轮询或 SSE；寻优结果分批返回。
4. 历史同步逐行 upsert，建议批量事务/`INSERT ... ON DUPLICATE KEY UPDATE`。

#### P1：文档与代码漂移

- `06-策略算法文档.md`：策略 A 反弹逻辑、desktop 文件路径（写在 `desktop/services/backtest.js`，实际是 `desktop/src/services/backtest.js`）均已过时。
- README/概述宣称「504 组三维寻优」，UI 实际只有两维；504 组来自离线脚本。
- 建议：以代码为准修订一篇「算法实现现状」，避免维护者被旧文档误导。

#### P2：数据与口径细节

1. **基准未应用 `scale_factor`**：组合标的价除了倍率，基准没有（`backtest.js` 阶段 3），当基准配了非 1 倍率时对比失真。
2. **流水去重过粗**：按 `(trade_time, etf_code, trade_direction)` 去重，同一天同标的同方向的第二笔（如先再平衡再策略）会被丢弃；且不同回测批次共用同一日期也会互相抑制。
3. **`weekly` 判定**：只认周五或最后一天，遇到周五休市则该周不评估。
4. **年化用自然日/365**：跨闰年略有偏差；区间极短（<1 天）返回 0。
5. **`history_data` 无复权标记**：前复权/不复权数据混存后无法区分，换源可能造成价格跳变。
6. **web 无鉴权**：CORS 只允许 localhost，适合本地/内网，但不适合直接公网部署。
7. **GET 结果接口一次性返回最多 500 条**，含 `params` JSON，长期使用后列表会变重。

#### P3：工程卫生

- 根目录存在 465 KB 的 `Table.xls`（样例数据），违反「根目录只保留 web/desktop/docs/.gitignore/README」的约定。
- `desktop/data/etf.db`（约 14 MB）在开发目录内（已被 `.gitignore` 忽略，但本地产物不应出现在交付物中）。
- 两套前端 `views/*.vue` 大量重复（Backtest.vue 约 5 万字节 × 2），虽然「代码不共享」是硬约束，但样式/图表配置重复维护成本高。
- `desktop/package.json` 打包图标使用 `assets/logo.png`，而项目经验记录 Windows 打包建议 `.ico`（≥256×256），可能导致图标异常。
- `.env` 与 `.env.demo` 同时存在于 `web/server`，`.env` 被忽略但需确认无真实密码入库。

## 七、改进建议（按落地顺序）

1. **统一回测内核**（P0）：把 web 的 `runBacktest / evaluateStrategyA / evaluateStrategyB / executeTrades / calcFee` 移植到 desktop，保持字段与语义一致；这是桌面版可信度的前提。
2. **给桌面版加一致性测试**：同一组参数在 web 与 desktop 上跑同一区间，断言总收益/回撤/成交笔数一致（允许浮点误差）。这是防止两端再次分叉的最低成本手段。
3. **性能优化**：主循环价格查找改为 `Map`；同步改批量写；寻优改为异步任务 + 进度接口。
4. **补齐口径**：基准也应用 `scale_factor`；流水去重加入 `batch_id`；`weekly` 改为「本周最后一个交易日」。
5. **文档纠偏**：修订策略算法文档与「504 组」表述，明确 UI 寻优仅两维、离线脚本才是 504 组。
6. **产品边界**：如果短期不移植策略，桌面版应在标题/页面显著提示「当前为买入持有回测」，并隐藏策略开关与调仓明细，避免误导。
7. **清理仓库**：移除 `Table.xls`、本地 db 与日志，把样例数据放到 `docs/` 或测试夹具目录。
